Customer Hub — How It Would Really Work on the Backend

A working Q&A on identity, provisioning, embedding, and search — written to separate what the prototype shows from what the production build actually requires.

Bottom line up front

The prototype proves the experience. The production version is mostly an integration and identity program, not a net-new app. Two parts are genuinely hard given how locked-down our systems are:

  • One login for all five is achievable, but only as fast as our slowest vendor's SSO + provisioning support.
  • Unified search is the real challenge. Doing it well — across five access-controlled systems, respecting each user's permissions — is not something I'd recommend we build from scratch. This is a buy-or-partner decision.

1 · Identity & Single Sign-On

Can one login realistically unlock all five destinations?

Yes — this is the most solvable part. It relies on a central identity provider (IdP) — Okta, Microsoft Entra ID, or Auth0 — as the single source of truth. Each destination (360Learning, the Zendesk support centers, the Zealot community, the missions/rewards platform) is registered as a service provider that trusts our IdP over SAML 2.0 or OIDC. The user authenticates once against the IdP; every destination then accepts that identity without a second prompt.

What has to be true for that to work?

  • Every vendor must support SSO on our tenant's plan (often a higher/enterprise tier — worth confirming per contract).
  • We standardize on one IdP and one identifier (usually corporate email) so the same person maps cleanly across systems.
  • The hub itself is also an SSO client — so opening the hub is the login, and links out inherit the session.

Does the "no second login anywhere" promise hold?

Practically, yes — with one honest caveat. The first time a user reaches a destination, some vendors bounce through an IdP redirect (a brief, invisible round-trip). After that the session is live. What we avoid entirely is re-entering credentials. The prototype's single sign-in button is the accurate promise; the redirects are plumbing the user won't notice.

2 · Provisioning & User Lifecycle

How do accounts actually get created in each system?

Two mechanisms, ideally combined. Just-in-time (JIT) provisioning creates the account on first SSO login from the identity token. SCIM keeps it in sync afterward — pushing joins, role changes, and (critically) deprovisioning when someone leaves, so access is revoked everywhere from one place.

Where's the friction?

This is where "locked-down" bites. Not every platform supports SCIM, and the ones that do may gate it behind a plan tier. Where SCIM is absent we fall back to API-based or scheduled sync — more custom code and more failure modes. Role mapping is the subtler problem: an "admin" in 360Learning is not an "admin" in Zendesk, so we need an agreed mapping from IdP groups to each system's roles, and an owner for it.

3 · The Locked-Down Pages (Embedding)

Why can't we just iframe the real pages inside the hub?

Because those platforms deliberately forbid it. Zendesk, 360Learning, and Zealot send X-Frame-Options / Content-Security-Policy: frame-ancestors headers that tell the browser to refuse rendering on any domain but their own. This is a server-side security control on their end — there is no client-side trick that overrides it, by design. Attempting to proxy around it (stripping headers on our own domain) is brittle, inherits their entire login/session/cookie behavior, and can break their app — not a path I'd recommend.

So what does "inside the hub" realistically mean?

Two viable patterns, used together:

  • Native surfaces — the hub renders content itself by pulling from each vendor's API (course lists, article previews, mission cards), styled in Momentus brand. This is what the prototype's Learning and Missions pages demonstrate.
  • Seamless hand-off — for deep interaction (taking a course, filing a ticket), the hub links out to the real system, and SSO makes that feel like one product rather than a logout/login.

4 · Unified Search — The Real Challenge

Can we build search across all five systems ourselves?

Technically we could stand up a basic version. But building search that is good — fast, relevant, complete, and above all permission-aware — across five separately access-controlled systems is a significant, ongoing engineering commitment. My honest recommendation is that we should not attempt to own this from scratch.

What makes it hard?

  • Permission trimming is the core problem. Our content is locked down — a given user may see some articles, courses, or community posts and not others. Unified results must reflect that specific user's entitlements in each system, at query time. Getting this wrong leaks restricted content; that's a security incident, not a bug.
  • Inconsistent APIs. Each vendor exposes search/content differently (or barely). Rate limits, pagination, and freshness vary. Community and the gamification platform in particular need API access confirmed before anything is possible.
  • Freshness vs. index. A central index is fast but can go stale and must be re-synced (and re-permissioned) constantly. Query-time federation is always fresh but as slow as the slowest vendor and harder to rank well.
  • Relevance & ranking. Merging results from five sources into one sensibly-ordered list is a whole discipline (this is what dedicated search vendors sell).

What are the realistic options?

Approach How it works Trade-off
A. Query-time federation (build) Hub calls each vendor's search API live and merges results. Always fresh; weak ranking; slow; we own all the permission logic.
B. Central index (build) Ingest all content into our own index (Elastic / OpenSearch / Azure AI Search). Fast & good ranking; we must sync + re-permission continuously; highest build cost.
C. Federated search platform (buy) A connector-based product — Coveo, Glean, Algolia, Elastic — that already handles ingestion, permission trimming, and ranking. Fastest to a trustworthy result; license cost; still needs per-connector config.
Recommendation

Lead with Option C. A federated search platform with pre-built connectors solves the two things that would otherwise sink us: permission-aware results and cross-source ranking. We keep the hub's branded UI and let the search layer do the heavy lifting. Treat Option A as a fallback only for systems a connector doesn't cover.

5 · Personalization & the "Adoption Agent"

Where does the "why you're seeing this" logic get its data?

From product-usage telemetry we largely already collect — via a product-analytics layer (e.g. Pendo, Gainsight PX, Amplitude) plus the entitlement data in each system. The recommendation cards in the prototype ("low adoption of Functions", "active at 1 of 6 venues") are exactly the kind of rule that reads a usage signal, compares it to a peer benchmark, and fires a nudge. That needs: (1) a reliable per-account usage feed, (2) a benchmark dataset, and (3) a lightweight rules or recommendation engine. None of this is exotic, but it's a dependency, not free.

6 · Security, Compliance & Data

  • Data handling: a central index or personalization store means we hold copies of content/usage data — triggering data-classification, retention, and residency review.
  • Permission integrity: the search layer must never out-run the source system's access rules (see §4).
  • Vendor posture: each integration is a data-sharing relationship — confirm SOC 2 / ISO, DPAs, and token scopes before connecting.
